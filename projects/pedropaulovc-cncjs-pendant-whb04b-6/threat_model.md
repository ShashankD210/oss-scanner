# Threat model

## Project, ownership, and scope

This enrollment covers Pedro's public MIT fork of the CNCjs pendant project, not authorization to represent upstream maintainers. Authenticated GitHub metadata identifies `master` as the default branch and `balthisar/cncjs-pendant-gamepad` as its parent (ultimate source `cncjs/cncjs-pendant-ps3`). The authenticated [comparison](https://github.com/pedropaulovc/cncjs-pendant-whb04b-6/compare/balthisar:master...pedropaulovc:master) observed on 2026-10-11 is 24 commits ahead, zero behind. Those commits are attributed to `pedropaulovc` and include `e6c655c09132343885e6babb9927467bb3729f72` (WebHID layer), `b964054823067ba2490db8dc1c204243e54ffc61` (same-origin CNCjs widget), and `088b0588803b6e8afc2d6edf627d11f52a8225b0` (browser-only cutover). Audited head: `813657d7bb4881598dbeb5534c30ad4fadd831c8`. This is actual fork-owned source scope, not an unchanged redistribution. No broad adoption or upstream maintainer approval is claimed.

The current app is static browser JavaScript: `web/whb04b-webhid.js`, its demo in `web/index.html`, and the CNCjs iframe integration in `web/widget/`. There is no remaining native Node pendant CLI or TypeScript compilation step. The nested `whb04b-6/src/WHB04BClient.csproj` is also in scope: it is a separate .NET 8 reference app, duplicated in Pedro's standalone protocol repository. Vendor documentation and split archives under `whb04b-6/vendor/` retain their vendor copyright; MIT source licensing does not confer ownership of those materials. Do not execute supplied vendor binaries or treat them as Pedro-maintained dependencies.

## Untrusted inputs and trust boundaries

* USB/HID reports are untrusted, including bytes from a malicious device presenting the expected VID/PID. Audit report length, identifiers, key/dial values, signed jog conversion, malformed state transitions, and display serialization. A VID/PID filter and browser device permission are not proof of trusted packet contents.
* The browser boundary is WebHID permission plus the origin running the driver. Audit connect/disconnect cleanup, event listener lifecycle, output report handling, and stale state. The driver writes pendant LCD reports; do not mistake this for merely read-only USB access.
* The custom widget obtains credentials/selected serial port from its CNCjs parent session and opens Socket.IO. Same-origin access to parent state is privileged, not an authorization mechanism for arbitrary embedding origins. Review credential exposure, origin assumptions, token handling, socket lifecycle, and how untrusted machine-state messages are rendered or converted to display data. CNCjs itself validates tokens; its authentication implementation is external, not owned by this enrollment.
* HID input becomes Grbl/CNCjs commands. This crosses a physical-actuation boundary: jog, resume/start, hold, reset, and other command mappings must not be treated as harmless UI events. Review units/sign/range handling, command gating, disconnected/stale machine state, unintended command repetition, and reconnect behavior. The scanner must never send commands to an actual CNC controller.
* The nested .NET application discovers devices through HidSharp, reads pendant input, and writes sample display data. Its parsing, asynchronous I/O, buffers, exception handling, and lifecycle are in scope. This console reference is not itself a CNCjs motion-control integration.

Concrete review entry points are `WHB04BWebHID._handleInput` and `parseInput` in the browser module, and `HidCommunication.ReadInput`, `WHB04BClient.HasDataChanged`, and `PendantInputData` in the reference app. Browser input is report ID `0x04`; signed jog and dial/key bytes require adversarial length/value cases. The widget's `readQuery` accepts both `token` and `host`; `readParentStore` reads the parent session; `listenParentMessages` handles token updates. Trace `message` origin/source checks and whether attacker-controlled `host` can receive a parent-derived token through `connectSocket`'s query. Source observations are review leads, not exercised exploit claims.

## Offline environment and safe exercise

The Dockerfile retains the complete checkout at `/src`, Node/npm, Python, Chromium, .NET 8 SDK/runtime, native Linux HID dependencies, and NuGet packages at `/opt/nuget/packages`. The root package has no npm dependencies and no build/test script beyond `serve`; the browser module is already source-form executable code. The nested .NET app is compiled in Debug to `/opt/whb04b-reference/linux`, with a framework-dependent `win-x64` review artifact at `/opt/whb04b-reference/win-x64`. Rebuild offline with `dotnet build whb04b-6/src/WHB04BClient.csproj --no-restore -c Debug`; offline package restore can use the retained cache if temporary test projects are added by the scanner.

The widget normally loads `/socket.io/socket.io.js` from its external CNCjs host; its source expects the 2.x client family. The image caches Socket.IO client 2.5.0 under `/opt/socketio-client-v2/node_modules/socket.io-client/` for isolated analysis. This client is not a substitute CNCjs server and does not establish integration compatibility or pin the external host's actual version. No CDN fetch or online CNCjs host is needed for parser/source review.

Serve static pages locally with `python3 -m http.server 8000 --bind 127.0.0.1 --directory /src/web` only in a fresh browser profile with no prior HID permissions: the demo and widget try to reconnect previously authorized devices on page load. Use the real browser module or direct parser/serializer code with synthetic report bytes, fake session strings, and inert capture-only command sinks. There is no automated test project/framework, test script, or synthetic HID suite in the inspected trees. The nested `TestClass.cs` is an empty-method style-order probe, not a test runner. Synthetic parser tests prove only the parser/serialization or command-generation behavior actually exercised, never device/runtime integration. Do not instantiate a client that opens hardware, invoke WebHID device selection, connect a real CNCjs session, use genuine tokens, or expose `/dev/hidraw`, USB devices, serial ports, or machine network access. Do not run the .NET console demo: it opens devices and sends LCD traffic.

Linux can run the net8.0 code and browser parser paths without hardware, but the image does not prove Linux HID permissions, browser WebHID device support, timing, Windows HID behavior, or physical machine safety. Windows-targeted publishing is compilation/review evidence only; no Windows runtime is supplied.

## Severity guidance

Treat attacker-controlled credential disclosure or command execution across an unauthorized origin/session boundary as high, escalating with demonstrated reach and consequences. Untrusted report handling that demonstrably causes unintended motion or bypasses an intended command gate is high; critical requires a supported credible safety-impacting attack chain, not merely the presence of jog functionality. Memory corruption in native HID dependencies should be assessed by controllability and reach. Parser crashes, resource leaks, or denial of pendant service are generally medium, with physical-context escalation justified explicitly. Legitimate motion by an authorized operator and the intentional same-origin CNCjs integration are not vulnerabilities by themselves.

## Leave alone

No real credentials, attached devices, CNCjs production sessions, vendor utilities, firmware flashing, machine motion, or external control effects. Do not report external CNCjs or upstream/vendor code as Pedro-owned without tracing the affected fork code and clearly stating attribution. Supply offline synthetic reproducers and distinguish source analysis, cross-compilation, and actual exercised runtime behavior.
