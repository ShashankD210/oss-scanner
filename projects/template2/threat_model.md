# Template Toolkit threat model

Template Toolkit compiles and renders template text with caller-supplied variables. Important untrusted inputs include template source or names, template variables, plugin and filter arguments, and file paths supplied through application configuration. Review the distinction between trusted application-authored templates and templates that an application allows an attacker to edit. Some applications intentionally grant templates powerful features; a report must state the actual trust boundary and relevant configuration.

Prioritize template name resolution and `INCLUDE_PATH` boundaries, including `ABSOLUTE` and `RELATIVE`; `INCLUDE`, `PROCESS`, `INSERT`, and wrappers; parser and compiled-template handling; output escaping and injection in specific contexts; and unsafe execution only where a supposedly restricted configuration allows it. Test both default Perl stash and XS stash behavior when relevant. The suite lives under `t/`; build with `perl Makefile.PL TT_QUIET=n TT_ACCEPT=y`, then run `make test` from `/src`.

Treat unauthorized file read, write, or code execution across a documented boundary as high or critical depending on impact and reachability. A concrete cross-user data leak or stored cross-site scripting path may be high; reflected injection and denial of service depend on deployment context. Do not call intended access to a trusted template, plugin, or explicitly enabled powerful feature a vulnerability without a boundary bypass. Describe exact inputs, configuration, output or side effect, and a minimal reproducer.

Use the private reporting channels in `SECURITY.md`; avoid public disclosure. Include a proposed patch and focused regression test, and preserve supported behavior where possible. As `AI_POLICY.md` requires, findings and patches need human maintainer review before release. Third-party plugins and application misuse are out of scope unless the distribution itself creates or fails to enforce a documented security boundary.
